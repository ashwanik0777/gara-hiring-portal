Section 01

Executive Summary

The GARA Innovation platform runs hiring and people operations in one secure web application: from a public careers site and candidate applications, through interviews and a supervised internship evaluation, to joining, employee records and HR self-service.

1.1Purpose of the platform

A visitor finds an opening on the public careers site, creates an account and applies. Staff screen the application, schedule interviews and record decisions with full history. Internship candidates complete a seven-working-day supervised evaluation; full-time candidates receive an offer letter and accept it electronically. When HR marks a person as joined, the person moves into the intern or employee workspace, where attendance, leave and payslips are available. Completed internships can lead to a certificate that anyone can verify with its code or QR.

For candidates
  • Account with emailed verification code
  • Versioned application forms per opening
  • Application tracker and interview slot booking
  • Offer letter download and electronic acceptance
For staff
  • Workspaces built for HR, managers, interviewers and mentors
  • Pipeline with enforced stage rules and history
  • Evaluations, joining and intern conversion reviews
  • Reports, hiring funnel and audited exports
For the organisation
  • No HR rule is invented: unapproved rules stay gated
  • Audit trail for consequential actions
  • Durable email delivery and scheduled reminders
  • One deployable application with clear module boundaries

Section 04

System Architecture

One Next.js application, organised as a modular monolith: clear business domains, shared utilities and replaceable provider adapters, deployed as a single unit on top of PostgreSQL.

4.1Architectural approach

The platform is a modular monolith (decision record ADR-0001). The team is small and the domain boundaries are still settling, so the operational cost of separate services is not justified. Server Components, Server Actions and route handlers give a natural server/client split inside one deployment.

Why not microservices

  • No service discovery, distributed transactions or multiple deployments to operate
  • Business rules still change as the product owner resolves open decisions
  • A clean modular monolith can be split later if scale demands it

Future extraction path

  • Each module's services/ already encapsulate its logic
  • A module can move behind an HTTP API without changing callers' contracts
  • Provider adapters make such a move incremental

4.6Request lifecycle

Every Server Action and route handler follows the same sequence. Layout checks only shape navigation; the security decision is always made again at the server boundary.

  1. 1
    RequestBrowser

    A form submits to a Server Action, or the browser calls a route handler. Server Actions carry Next.js' built-in origin check.

  2. 2
    Authenticatesrc/lib/auth

    requireAuth() resolves the Better Auth session, memoised once per request. Sessions with a temporary password are refused until /set-password succeeds.

  3. 3
    AuthorizeGuards and services

    Role rule, granular permission flag (requirePermission, assertPermission) and record scope: own record, supervised intern or assigned interview.

  4. 4
    ValidateZod schema

    All untrusted input is parsed on the server. Client-side validation exists only for user experience.

  5. 5
    Enforce business rulesFeature service

    Allowed-transition maps, flow-owned statuses, self-dealing blocks and policy gates. Conditional updates prevent two requests from applying the same change.

  6. 6
    PersistPrisma transaction

    The change, its history row, the audit entry, queued email and any scheduled job are written together or not at all.

  7. 7
    RespondSafe result

    toActionError or toSafeErrorResponse return only operational messages; details are logged on the server. Queued email is delivered after the response.

Section 06

Recruitment Workflow

From a published opening to a hiring decision: versioned application forms, accountable stage changes, interviews with calendar invites, candidate self-scheduling and measurable sources.

6.1Openings and dynamic application forms

An opening describes a job or internship: title, URL slug, department, type (INTERNSHIP or FULL_TIME), location, workplace (REMOTE, HYBRID, ON_SITE), description and requirements. Its status follows a fixed, server-enforced lifecycle.

DraftPublishedPausedPublishedorClosed (final)
AspectHow it works
Versioned formsEach application form is an immutable OpeningFormVersion. An application stores the version it was submitted against and a snapshot of the answers, so later edits never reinterpret past submissions.
PreviewStaff preview the candidate view of an opening before publishing (/admin/openings/[id]/preview).
Safe validationAnswers are validated on the server against the form definition. Staff-defined patterns are checked for catastrophic backtracking when saved and are never executed if unsafe; checked input is capped at 300 characters.
Public visibilityOnly published openings appear on /careers. Lists and detail pages are cached (refreshed every 5 minutes) and invalidated immediately when staff change an opening.
Search enginesOpening pages embed escaped JobPosting structured data for Google Jobs; /sitemap.xml lists published openings and /robots.txt blocks portals, authentication screens, APIs and apply forms.

6.2Application submission

  1. 1
    Find an openingVisitor

    The visitor browses /careers. Links shared with ?source=linkedin or utm_* parameters keep their source through sign-in.

  2. 2
    Sign in or registerCandidate

    An account is required before applying. New accounts confirm their email with a six-digit code.

  3. 3
    Complete the formCandidate

    The form is rendered from the published version; every answer is validated again on the server.

  4. 4
    Provide the resumeCandidate

    Default link mode: an https share link (Google Drive, OneDrive, Dropbox) validated on the server. Upload mode on an own server: PDF, JPEG or PNG, signature-checked, virus-scanned and stored privately.

  5. 5
    SubmitSystem

    Limited to 5 submissions per hour per user. The application receives a reference code and the status SUBMITTED; the confirmation email is queued in the same transaction.

  6. 6
    TrackCandidate

    The candidate sees only their own applications and the candidate-facing messages. Internal notes and interviewer feedback are never shown.

Policy gate · OD-005

A second application to the same opening is currently allowed. Duplicate-application rules, required profile fields and account deletion await the product owner's decision.

6.5Bulk actions, sources and the hiring funnel

Bulk actions

ADMIN or HR with canApplications can move or reject up to 100 selected applications. Each item passes the single-transition checks; the result lists moved and skipped items with reasons, and every item is audited.

Source tracking

Source parameters are normalised on the server (for example LINKEDIN, CAREERS_PAGE, OTHER). The candidate's own "How did you hear about us?" answer takes precedence.

Hiring funnel

Stage conversion, drop-off, time in stage, time to hire (calendar days to HIRED) and sources, filtered by date, opening type and opening, with an audited CSV export.

Section 07

Internship Programme

Selected internship candidates complete a supervised evaluation of seven working days. A human decision, an onboarding checklist and HR's "Mark as joined" turn a successful candidate into an intern, who can later be converted to full time.

7.1Seven-working-day evaluation

Pending triggerIn progressUnder reviewPassedorFailed
ElementBehaviour
Start triggerThe countdown never starts automatically. ADMIN, HR or the assigned supervisor starts it explicitly, which stamps the start date and schedules seven daily checkpoints (OD-001).
Working daysWorkingDayService counts working days on a configurable calendar: working weekdays (default Monday to Friday), holiday dates and time zone. No official holiday list is assumed (OD-002).
CheckpointsOne checkpoint per day (1 to 7), each PENDING, SUBMITTED, REVIEWED or BLOCKED. The intern submits notes; the supervisor reviews. Daily reminders go to both at 09:00.
OutcomePass or fail is an authorised human decision with review notes. No score or elapsed time decides automatically. A failed evaluation returns the person to the candidate stage. The EXTENDED outcome exists in the schema but is blocked until an extension policy is approved (OD-003).
Supervisor scopeMentors, managers and interviewers act on evaluations only for interns they supervise.

7.2From selection to joining

13.2Authentication

ControlImplementation
PasswordsHashed by Better Auth (scrypt). Reset uses a single-use link valid for 1 hour; the response never reveals whether an account exists, and completing a reset revokes every session.

13.3Authorization

  1. Every Server Action and route handler checks authorization on the server, not only authentication.
  2. Records are scoped: candidates see their own applications, employees their own records, interns their own work; interviewers see assigned applications and supervisors their own interns.

  6. Self-dealing is blocked: nobody selects their own application, approves their own leave or touches their own payout record.

15.3Engineering standards

Business rules

Never invent recruitment, HR, attendance, leave, payroll, evaluation, certificate or retention rules. Missing rules go to docs/OPEN_DECISIONS.md; work continues only where it is safe.

Code quality

TypeScript strict mode; no any, no @ts-ignore and no disabled lint rules without a narrow, documented justification.

Server boundaries

Authenticate, authorise, validate, enforce transitions and return safe results in every Server Action and route handler. No business logic in Client Components.

Data integrity

Constraints, foreign keys and indexes used intentionally; transactions for multi-record changes; explicit status transitions with history.

Evidence

"Implemented", "tested", "configured" and "deployed" are different states. Nothing is reported as working without evidence.

Working process

One approved phase at a time; inspect git status before changes; no destructive commands without explicit approval.

17.6Performance design

Data access

  • Session and permissions read once per request
  • Every staff list loads one page of at most 50 rows, with the total counted in parallel; page numbers are capped
  • Reports aggregate in PostgreSQL; exports stop at 10,000 rows
  • Composite indexes back the paginated queries

Rendering

  • Static shells paint first; the session streams in behind a skeleton
  • Public openings are cached and invalidated by tag on change; private pages are never cached
  • Heavy dialogs and report charts load on demand
  • A thin progress bar appears only for navigations longer than 120 ms
